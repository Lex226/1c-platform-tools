# ADR-0002: Версионирование документации через frontmatter, а не через папки/версии в дереве

- Статус: Принято
- Дата: 2026-08-11
- Контекст исследования: Model Council (GPT-5.6 Sol Thinking, Claude Opus 5 Thinking, Gemini 3.1 Pro Thinking) — единодушный вывод по отказу от папок `versions/`, расхождение по месту хранения версионной дельты

## Контекст

У платформы 1С:Предприятие есть номера сборок (например, 8.3.27.1859), а у
подсистемы "Инструменты разработчика" (RDT1C) — собственный, независимый
цикл релизов (например, 8.20.1, 8.19.1). Это две независимые оси
версионирования. Поведение инструментов подсистемы часто зависит от
платформы, режима базы данных и конкретной конфигурации — что подтверждают
issues в tormozit/RDT1C, где баги фиксируются с обязательным указанием
этих трёх параметров.

Папочная модель версионирования (`versions/8.3.x.x/<tool>.md`) даёт
90–95% дублирования контента между минорными билдами платформы, потому что
поведение инструмента почти не меняется между ними. При двух независимых
осях версионирования (платформа × RDT1C) папочная модель превращается в
декартово произведение версий, что делает дерево нечитаемым и создаёт
риск: агент не понимает, какая копия страницы каноническая, и правит
устаревшую.

## Решение

Версионная информация хранится **только в YAML-frontmatter** канонической
страницы, а не в структуре каталогов:

```yaml
---
title: "Ис() / Исследовать() — вызов Исследователя объектов"
status: promoted # raw | promoted
promoted_to: null # ссылка на sessions/-снапшот, если применимо
platform_verified_on: ">=8.3.27.1859"
rdt_version: "8.20.1"
verification: reproduced # hypothesis | observed | reproduced | externally-confirmed
discarded: [] # опровергнутые гипотезы, не удалять из истории знания
---
```

Если для конкретной страницы накопится 3 и более подтверждённых
расхождения в поведении между разными сборками платформы, вводится
дополнительный слой `docs/compatibility/platform/<version>/<tool>.md` —
но не раньше. До этого момента папка `compatibility/` не создаётся.

Шкала верификации обязательна для любого утверждения о поведении
инструмента: `hypothesis → observed → reproduced → externally-confirmed`.
Запрещены формулировки вида "ИР всегда...", "работает на всех версиях..."
без явного статуса `externally-confirmed`.

Матрица совместимости (`matrix.yml` или аналог) не ведётся вручную, а
генерируется скриптом из frontmatter всех страниц — чтобы не расходиться
с реальным содержимым документации.

## Последствия

- В дереве репозитория не появляются каталоги `versions/`.
- Кросс-версионная ретроспектива выполняется через `git log -S "term"` по
  каноническим страницам, а не через checkout старых веток/тегов.
- Git-теги (например, `plat-2026-08`) используются только как неизменяемые
  снапшоты состояния репозитория на момент времени (для GitHub Release),
  а не как хранилище версии документации.
- Поле `discarded:` обязательно сохраняет опровергнутые гипотезы внутри
  страницы — это предотвращает повторную проверку тупиковых версий
  поведения инструмента в будущих сессиях.
